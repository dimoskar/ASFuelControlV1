# Step 5: provider integration

Implemented on 2026-10-15 in the new host project `ASFuelControl.Invoicing` (.NET Framework 4.6), registered in the solution. It composes the step 4 mapper, the three real adapters and the step 3 SQL stores. The running Windows/PrintAgent send path remains on the legacy implementation until the fiscal-device, POS and PrintAgent steps are completed. Do not run the old and new workers against the same invoice: the old worker does not participate in the new document lease.

## Host entry points

| Entry point | Behavior |
|---|---|
| `ProviderSubmissionService.Send` | Holds one SQL invoice lease across history checks, source loading/mapping, validation, credentials, submission and durable outcome. First issues require a host source and explicit route. Existing accepted/unknown/queued/sending attempts go through recovery without rereading mutable invoice data or using the newly selected route. |
| `Recover` | Resolves the original provider, environment, issuer, branch, account, endpoint and credential profile from saved routing metadata. No invoice POST or payment is initiated by this path. Missing historical metadata/credentials fails closed. |
| `UploadIlydaPdf` | Uses the saved Ilyda route and accepted invoice. PDF upload remains separate from issuance; a failure leaves the accepted fiscal result intact, and a saved successful upload is reused. |
| `LoadParentEvidence` | Reads durable accepted submission evidence and historical scope for the mapper. Rejects missing/uncertain issuance, invalid MARK and any accepted or unresolved cancellation. It does not use legacy MARK-only rows or call a provider. |
| `DatabaseInvoiceSource` | Loads the real invoice and navigations inside a live Data context, checks legacy history and the type's `SendToMyData` flag, captures supplied mapping settings, verifies their environment and calls `HostInvoiceMapper`. No number allocation, entity mutation or `SaveChanges` occurs. |

The `IInvoiceSubmissionSource` boundary permits testing and later transaction integration. Its production implementation rejects **any** existing legacy `MyDataInvoice` row, even a failed/empty summary, and any existing printed flag, signature or QR data. Those records require historical reconciliation/import; an empty new journal is not permission to resend them. Parent invoices and their evidence must be loaded consistently through the mapping settings callback while the source Data context is alive.

`ProviderSubmissionResult.Accepted` requires both an accepted journal state and a successful response. Acceptance refers only to the original invoice submission; payment, subsequent cancellation and physical printing retain their separate histories and must be checked by the final orchestrator.

## Route and credential handling

`ProviderRoute` is an immutable, non-secret descriptor: provider key, test/production selection, issuer VAT/branch, credential-profile identifier, provider account and (for myDATA) base URL. The default provider endpoints are generated by the existing adapters; myDATA overrides require HTTPS and cannot contradict a known production/test endpoint. A route's company VAT/branch must match the mapped invoice.

`IProviderCredentialsResolver` must resolve **the supplied historical route**, including its account/profile, without falling back to current settings. Secrets are copied into fresh adapter options per operation. No legacy provider singleton or static credential initialization is used. Keep old credential profiles available for recovery, or explicitly reconcile invoices whose old credentials can no longer be used.

The account field identifies the myDATA user, iTimologia subscription, or Ilyda username (older routes may identify an API account). Do not put API keys, tokens or passwords in account/profile names. The resolver supplies myDATA subscription key, iTimologia master token, and Ilyda password. The adapter retains API-key support for historical Ilyda attempts; the step-9 settings form now creates username/password profiles only. Existing Arbitrans settings are not silently interpreted as direct Ilyda credentials. Configuration storage/UI for these routes belongs to step 9.

The service performs shared model validation and offline channel serialization before authentication. It then constructs the adapter with the corresponding SQL submission store and an invoice-scoped SQL HTTP logger. The adapter journals the exact transmitted payload before the external invoice call. Authentication bodies and authorization headers are omitted from the HTTP journal.

## Retry, recovery and adapter fixes

| Channel | Implemented recovery and limits |
|---|---|
| myDATA | Accepted responses are read from saved evidence. An uncertain submission remains blocked; the adapter's transmitted-document API is available for a later explicit reconciliation procedure, but this step does not infer acceptance or rejection from a missing lookup. |
| iTimologia | Accepted results are reused locally. Unknown/conflict/timeout lookup uses the stable external invoice ID. A successful lookup must include the matching external identity and a positive numeric MARK; cancellation/mismatch/missing identity leaves it unknown. Lookup results now append a durable submission revision. A 404 never authorizes resubmission. |
| Ilyda Direct | Accepted results are reused locally. Queued invoices use the existing queue lookup, verifying invoice UID, seller VAT and invoice number before acceptance. An absent queue record or ordinary uncertain submission does not authorize a resend. Malformed original response bodies are now retained in the submission history. |

A definitive rejection does not automatically trigger another invoice attempt. `retryRejected: true` is an explicit host workflow decision after correcting the source; the service requires the original route and fiscal identity (series, number, date and type) to remain unchanged. Earlier requests/responses remain in history. iTimologia's protocol-specific authentication retry after HTTP 401 is permitted only after its rejection was durably saved.

iTimologia previously swallowed failures while saving the final fiscal outcome. It now propagates that persistence failure into an unsuccessful operation; the saved `Sending` record continues to block a duplicate, and recovery uses GET. A successful provider reply alone is not permission to report durable acceptance or print.

## Persistence and SQL Server 2008 R2

No table, migration or SQL batch was added or changed in this step. The existing JSON snapshots gain an optional `RoutingContext` field through `IRoutedSubmission`. The host records a versioned route and fiscal identity there on the initial attempt. SQL stores reject changes to that field on later revisions. Credentials are not stored in it.

Existing attempts without this field are held for reconciliation instead of being relabelled with current settings. The SQL Server 2008 R2 requirement is unchanged: metadata serialization occurs in .NET, stored in the existing `nvarchar(max)` snapshots. The regression suite checks production SQL with the SQL-100 parser; database tests run at compatibility level 100 on modern LocalDB. Native SQL Server 2008 R2 runtime validation remains outstanding.

## Boundaries for subsequent steps

- Card/IRIS submission is blocked before authentication until step 7 connects the payment coordinator. This prevents bypassing payment just because a provider accepts an offline payload.
- Existing signing, provider-signature session, payment, cancellation or print history blocks a **new** submission attempt in this standalone service. Steps 6–8 must replace that conservative gate with verified stage prerequisites inside the same outer lease. Recovery of an existing submission remains read-only and available.
- Numbering stays in the host transaction. The source requires already allocated, saved identity. Direct myDATA cancellation must be connected to the separate cancellation journal by the final workflow; calling the raw adapter cancellation API bypasses that journal and is not a host cancellation entry point.
- PrintAgent activation, compatibility projections into legacy entities, printing and cancellation orchestration remain in step 8. No printed flag, signature, MARK or QR field is written to a legacy invoice by this service. A UI/display failure must not cause a new provider submission.
- Historical migration and route/credential UI remain in step 9. Live provider acceptance, operating-system HTTPS/TLS configuration and physical-device/POS/printing behavior require deployment/integration validation.
